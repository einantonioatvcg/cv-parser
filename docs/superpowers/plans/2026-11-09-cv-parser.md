# cv-parser Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Un microservicio local en Python que lee CVs en PDF, `.docx` y `.doc`, en español e inglés, y devuelve JSON genérico con un contrato versionado, más una medición con CVs de muestra.

**Architecture:** FastAPI en Docker, sin estado y configurado por variables de entorno. Un pipeline convierte cualquier formato en líneas con formato, las divide en secciones y entradas con reglas propias y devuelve `extracted`. Ningún consumidor aparece en el código ni en el contrato.

**Tech Stack:** Python 3.12, FastAPI, pdfplumber, python-docx, LibreOffice, pytest, Docker.

**Spec:** `docs/superpowers/specs/2026-11-09-cv-parser-design.md`

## Global Constraints

- Nada se sube: cero `git push`. El repo no tiene remoto y `.git/hooks/pre-push` lo bloquea. Rama `local/cv-parser`.
- El servicio no llama a terceros, no usa LLM y no guarda nada de lo que procesa.
- Nada de ningún consumidor en `src/` ni en el contrato.
- Los CVs reales solo viven en `<muestra>/`; nunca en el repo, un fixture o un test.
- Los logs no llevan texto del CV ni nombre de archivo.
- Un campo vacío es mejor que uno incorrecto: nunca inventar mes, país ni entradas.
- Variables: `CV_PARSER_CORS_ORIGINS` (vacío), `CV_PARSER_MAX_BYTES` (`10485760`), `CV_PARSER_API_KEY` (vacío), `CV_PARSER_CONVERT_TIMEOUT` (`60`).
- Puerto `127.0.0.1:8010`. `parser_version` y `version` son `0.1.0`.
- Todo comando Python corre dentro del contenedor: `docker compose run --rm api <comando>`, desde `<repo>`.
- Cada commit termina con la línea de atribución indicada por la sesión.

## Review Focus

- Datos personales y referencias de CVs mexicanos (`Fecha de nacimiento: 12/05/1990`, `CURP`, `REFERENCIAS PERSONALES`) nunca se vuelven empleos, estudios ni sus fechas. Test en Task 8.
- CV sin ningún encabezado reconocible: `status` `partial`, aviso `no_sections`, `meta.sections` vacío y sin entradas inventadas. Test en Task 9.
- Entradas sin fecha: se conservan con fechas vacías y confianza baja, sin perderse ni fusionarse con otra. Test en Task 8.
- Documento sin texto o subida de 0 bytes: `.docx` vacío da `unreadable` con `empty_document`; 0 bytes da `400`. Test en Task 9.
- Texto con espacios duros, ligaduras (`ﬁ`), acentos separados o todo en mayúsculas se interpreta igual que el texto limpio. Tests en Tasks 3 y 6.

7. Confianza: 0.4 con fechas, 0.3 por cada uno de los otros dos datos clave (puesto y empresa, o nivel e institución).

El usuario copia sus CVs en `originales/`.

- [ ] **Step 2: Sortear y revisar cobertura**

Run: `docker compose run --rm -v <muestra>:/muestra api python eval/run_eval.py --sample-dir /muestra --init`
Expected: `split.json` e `ids.json`, y conteos por grupo. Si faltan `.doc`, inglés o varias columnas en la reserva, decírselo al usuario; esos casos solo quedan probados con fixtures.

- [ ] **Step 3: Escribir las respuestas esperadas de afinado**

Solo para los CVs de `tuning`. Convertirlos a PDF con `soffice` dentro del contenedor, en `/muestra/render/`, leerlos con la herramienta Read y escribir `expected/<id>.expected.json` a partir del CV, sin mirar la salida del parser. El usuario revisa unos 3. Los CVs de `reserve` no se abren todavía.

- [ ] **Step 4: Rondas de afinado (máximo 3)**

Run: `docker compose run --rm -v <muestra>:/muestra api python eval/run_eval.py --sample-dir /muestra --split tuning`
Revisar los errores. Por cada patrón, escribir primero un test con datos inventados que lo reproduzca, corregir y hacer commit. Antes de cada commit, `git diff --cached` para confirmar que no entra ningún dato de la muestra.
Expected: parar al alcanzar las metas o al completar la tercera ronda, lo que ocurra primero.

- [ ] **Step 5: Congelar y abrir la reserva**

Run: `git tag parser-congelado`
Con el parser congelado, leer los CVs de `reserve`, escribir sus `expected.json` y correr:
Run: `docker compose run --rm -v <muestra>:/muestra api python eval/run_eval.py --sample-dir /muestra --open-reserve`
Expected: reporte final con veredicto. El parser no se modifica después de esto para mejorar esta cifra.

- [ ] **Step 6: Reportar al usuario**

Dar cifras de la reserva por formato, idioma, columnas y sección, los patrones que fallan, los CVs ilegibles, el veredicto y si conviene seguir con reglas o conectar OpenAI solo para secciones de baja confianza. Sin datos personales en el texto que se pueda compartir.

- [ ] **Step 7: Pedir confirmación para borrar**

Preguntar al usuario si borra `<muestra>/`. No borrar sin su confirmación.
